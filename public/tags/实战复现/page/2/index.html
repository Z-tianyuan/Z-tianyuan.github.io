    SSRF 探究与挖掘过程（SRC 目标）

    April 6, 2026
    漏洞挖掘
    实战复现, Web安全

    📍 第一步：寻找“代购”入口 (Locate the Sink)#

    你要寻找一切让服务器去发起网络请求的功能点。常见的重灾区有：

    • URL 传参点： 像刚才的 stockApi=，或者 url=, domain=, endpoint=。

    • 图片加载/头像上传： “提供图片 URL 自动下载并设置为头像”的功能。

    • PDF 导出器： 将网页转换成 PDF 的功能（很多 HTML 转 PDF 的引擎允许内嵌远程资源）。

    • Webhooks 订阅： 允许你输入一个回调地址，服务器有事会向这个地址发请求。

    📍 第二步：回显探针 (Proof of Concept)#

    找到入口后，不要急着打内网，先证明它真的能发请求。

    • 测试方法： 把参数改成你自己控制的公网服务器地址（比如你自己买的云服务器 IP，或者使用 Burp Collaborator 提供的临时域名）。

    • 判定： 如果你的服务器收到了来自目标机器的 HTTP 请求或 DNS 查询，恭喜你，盲打成功，存在 SSRF 漏洞！

    📍 第三步：探测内网轮廓 (Internal Reconnaissance)#

    这就是你刚才用 Python 脚本做的事情。一旦确认 SSRF 存在，立刻开始“扫街”。

    • 猜网段： 尝试常见的内网私有地址段，如 192.168.x.x, 10.x.x.x, 172.16.x.x。

    • 探本机： 永远不要忘记测试 127.0.0.1 和 localhost，看看服务器本机有没有藏着未授权的后台（就是你的第一个 SSRF 实验）。

    访问控制漏洞狩猎（SOP）

    April 5, 2026
    漏洞挖掘
    Web安全, 实战复现

    🗺️ 第二部分：实战狩猎 SOP (你的专属挖洞说明书)#

    在接下来的真实漏洞赏金挖掘中，无论你面对的是电商、金融还是企业 OA 系统，只要遇到有“账号登录”的地方，请直接掏出这套测试流程：

    📍 准备阶段：建立对照组 (The Setup)#

    永远不要只用一个账号挖越权！你需要准备：

    1. 账号 A（攻击者）： 你的主测试账号。

    2. 账号 B（受害者）： 用来验证横向越权的平级账号。

    3. （可选）管理员账号： 如果目标系统允许你注册企业版/管理员版，注册一个。

    📍 第一步：地毯式收集“身份标识” (Reconnaissance)#

    登录账号 A，把网站所有功能点一遍（修改资料、收货地址、查看账单、上传文件）。

    • 紧盯 Burp Suite，寻找关键参数： user_id=, uid=, order_no=, email=, role=。

    • 收集账号 B 的信息： 记录下账号 B 的上述所有参数备用。

    📍 第二步：执行横向越权测试 (IDOR Hunting)#

    将账号 A 抓到的数据包发送到 Repeater。

    1. 直接替换： 把包里的 ID 换成账号 B 的 ID，发送。

    2. 看结果：

      • 成功返回账号 B 的数据（200 OK） -> 拿下横向越权！

      • 返回 403 / 401 -> 防御有效，进入下一步。

      • 返回 302 重定向 -> 注意！ 切换到 Burp 的 Response 窗口，仔细看看 302 的 Body 里有没有泄漏 B 的数据！

    访问控制漏洞的探索路径

    April 1, 2026
    漏洞挖掘
    Web安全, 实战复现
    🗺️ 访问控制/越权狩猎标准路径 (SOP)#

    📍 第一步：建立“多重身份”观测站 (The Setup)#

    在挖掘越权之前，你必须拥有对比参照物。不要只拿一个账号瞎点。

    1. 注册账号 A（攻击者）： 比如 attacker:123。

    2. 注册账号 B（受害者）： 比如 victim:123。

    3. 寻找高权限入口： 如果网页上有公开的管理员账号密码（如 administrator:admin），也登录它备用。

    4. 操作：打开三个不同的浏览器（或使用隐私模式/多账号插件），分别登录这三个账号。

    📍 第二步：雷达扫描，锁定“敏感标识符” (Mapping & Recon)#

    操作账号 A，在网站里像正常用户一样闲逛：修改资料、下订单、看账单、发私信。 此时，眼睛死死盯着 Burp Suite 的 HTTP History，寻找以下特征的参数：

    • 数字 ID： ?user_id=1234 或 {"order_id": 5678} (最经典的 IDOR 目标)。

    • 用户名： /profile/carlos 或 ?account=wiener。

    • 文件路径： ?file=receipt_101.pdf。

    • 角色标识： {"role": "user"} 或 {"isAdmin": false} (纵向越权的高价值目标)。

    📍 第三步：发动“横向降维打击” (Horizontal IDOR Test)#

    一旦你在账号 A 的请求包里看到了代表身份的 ID（比如 id=101），立刻送到 Repeater。

    1. 直接替换： 把 id=101 改成账号 B 的 id=102。

    访问控制漏洞与权限升级

    March 30, 2026
    漏洞挖掘
    Web安全, 实战复现

    🧠 第一部分：你这周打下的“江山” (漏洞全景归纳)#

    别看靶场名字五花八门，其实它们全部可以归入三大核心流派。顺便提一句，最后一个“基于加油器的访问控制”，其实是机器翻译把 Referer (引用页) 错翻成了加油器（Refueler/Referer 谐音梗），这也算是安全圈里的一大笑话了！

    🗡️ 流派一：纵向越权 (Vertical Escalation) —— “草根强闯董事会”#

    这个流派的核心是：你是一个普通用户，但你强行执行了管理员的功能。

    • 裸奔的接口： 依靠前端隐藏或不可预测的 URL 来保护后台（比如 /administrator-panel-yb556），一旦被你翻源代码或 robots.txt 找到，直接访问就进去了。

    • 参数篡改 (Parameter Tampering)： 比如修改个人资料时，强行抓包塞入 roleid=2 或者 Admin=true，利用了后端框架**“批量赋值”**的坏习惯。

    • HTTP 魔法绕过： * 方法欺骗： 前端保安只拦截 POST，你就右键一键转成 GET 绕过。

      • 框架解析差异： 用 X-Original-URL 头部把真实的危险路径藏起来，骗过第一层路由。

      • 头部伪造： 就是那个搞笑的“加油器”（Referer 欺骗），让服务器误以为你是从内部管理页面跳过来的。

    🛡️ 流派二：横向越权 (Horizontal IDOR) —— “隔墙偷看邻居信”#

    这个流派的核心是：大家都是平级用户，但你通过修改标识符，偷看了别人的私密数据或动了别人的资产。

    • 傻瓜式遍历： 最经典的 id=wiener 改成 id=carlos，或者订单号 1001 改 1002。

    • 不可预测 ID 的破局： 如果 ID 是长串 UUID 猜不到怎么办？你学会了寻找信息泄露点。比如在前端 JavaScript 变量里，或者像实验中那样去猜 1.txt 聊天记录，从中把别人的 UUID 或密码翻出来。
