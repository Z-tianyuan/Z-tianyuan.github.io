    第一天

    好的，我把今天做的三件事彻底讲透。

    一、扫描链路验证

    做了什么： 用 Nuclei 扫本地 HTTP 服务，把 JSON 结果喂给 ai_filter.py。

    原理：

    ┌────────────┐ ┌──────────────────┐ ┌───────────┐ │ Nuclei │ ──► │ results/*.jsonl │ ──► │ qwen3:8b │ │ 发送探测包 │ │ 每条是一行JSON │ │ 逐条分析 │ └────────────┘ └──────────────────┘ └───────────┘ │ ┌──────▼──────┐ │ 真实 / 误报 │ └─────────────┘

    为什么这么设计： Nuclei 输出的每条 JSON 包含完整的 request（发了什么请求）和 response（服务器回了什么），这恰好是 LLM 做判断所需的全部上下文。不需要额外捞数据。

    使用方法：

    1. 扫目标，输出 JSONL#

    nuclei -target http://目标 -t 模板目录 -jsonl -silent -o results/scan.jsonl

    2. 跑 AI 过滤#

    cd /d/NucleiAI && python tests/test_filter.py

    二、Prompt 改进

    做了什么： 重写了 ai_filter.py 里的 system prompt，让 LLM 先分类、再研判。

    改进前的问题： 旧 prompt: “判断这个漏洞是否真实存在” 问题: 技术检测类结果（如"检测到 Python"）被当作漏洞去判断 → AI 困惑 → 全判误报

    改进后的逻辑： 新 prompt 三步走: 第一步: 看 tags 字段，判断类型 tech/discovery → 技术识别类 vuln/cve/rce → 漏洞利用类 exposure/misconfig → 配置暴露类

    第二步: 套用不同类型的判断标准
        技术识别: 只要响应里确实有对应特征 → 不是误报
        漏洞利用: 检查请求/响应是否证明漏洞真正被触发
        配置暴露: 检查返回的是真实配置还是登录页/404

第三步: 输出结构化 JSON {finding_type, is_false_positive, confidence, reason}

    关键代码（ai_filter.py 第 83-86 行）：

    兜底保护: 技术识别类就算 AI 判错了也自动修正#

    if verdict.get(“finding_type”) == “tech” and verdict.get(“is_false_positive”): verdict[“is_false_positive”] = False verdict[“reason”] = “[自动修正] 技术识别类结果不标记为误报”

    为什么这么设计： 不能让 AI 独裁。代码里加了一层规则兜底——技术识别类结果永不当误报。这就是「AI + 规则引擎」混合架构的核心思想。

    三、自定义模板

    做了什么： 手写了 5 个 YAML 模板，每个展示一种匹配技���。

    模板的本质： id: 唯一标识 info: name: 漏洞名称 severity: info|low|medium|high|critical tags: [分类标签] ← 这个给 AI 判断类型用

    http: ← 定义请求 - method: GET path: “/xxx”

    matchers: ← 定义判定逻辑 - type: word ← 五种匹配方式之一 part: body ← 在响应的哪个部分找 words: [“关键词”]

    五种匹配方式对比：

    ┌────────┬────────────────┬────────────────────────────────────────────────────────────┐ │ 技法 │ 做什么 │ 什么时候用 │ ├────────┼────────────────┼────────────────────────────────────────────────────────────┤ │ word │ 响应里找关键词 │ 特征明确，如 “admin”、“password” │ ├────────┼────────────────┼────────────────────────────────────────────────────────────┤ │ regex │ 正则表达式 │ 动态内容，如版本号 Python/3.\d+.\d+ │ ├────────┼────────────────┼────────────────────────────────────────────────────────────┤ │ status │ HTTP 状态码 │ 判断页面是否存在，如 200 vs 404 │ ├────────┼────────────────┼────────────────────────────────────────────────────────────┤ │ dsl │ 复杂组合表达式 │ 需要 status_code==200 AND len(body)>1000 AND contains(…) │ ├────────┼────────────────┼────────────────────────────────────────────────────────────┤ │ binary │ 二进制匹配 │ 文件头、图片等非文本内容 │ └────────┴────────────────┴────────────────────────────────────────────────────────────┘

    为什么 5 个全命中： 每个模板的匹配条件都精准对应了 Python HTTP 服务的实际响应内容——Server 头包含 Python、body 包含 Directory listing、status_code 是 200。

    今天三件事的关系

    自定义模板 ──定义检测规则──► Nuclei 扫描 ──输出JSON结果──► AI 过滤引擎 │ tags 字段决定判断标准 (你今天写的模板 tags 里有 demo/tech 等)

    一句话总结今天：你搭建了一条从「定义规则 → 自动扫描 → AI 研判」的完整链路，现在缺的只是把这条链路装进 Web 界面里。
